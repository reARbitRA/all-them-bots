Key Telegram facts I’ll rely on (so you don’t build the wrong payment/security flow):
- For webhooks, Telegram supports setting a **`secret_token`** and will include it in the header `X-Telegram-Bot-Api-Secret-Token` on every webhook update.   
- For payments (physical/services): your bot must answer **`pre_checkout_query` within 10 seconds** or the transaction is canceled; deliver after `successful_payment`.   
- For **digital goods/services**, transactions must use **Telegram Stars** with currency code **`XTR`**; flow is `sendInvoice(XTR)` → `pre_checkout_query` → `successful_payment`.   
- For Mini Apps, **never trust `initDataUnsafe`**; send `initData` to backend and validate it.

# Shared production blueprint (use for almost all #126–#150)

## A) Deployment (cheap + reliable)
- **FastAPI (Python) + aiogram** for bot
- **PostgreSQL** (Supabase/Neon/Railway are quick)
- **One “jobs” table** for reminders + scheduled work (instead of Redis/Celery at MVP)
- **Two processes**:
  1) `bot_webhook` (handles Telegram updates)
  2) `job_runner` (runs every minute, executes due jobs)

## B) Job runner pattern (reminders / digests / cooldowns)
**Table:**
- `jobs(id, run_at, type, payload_json, status, attempts, last_error)`

**Runner logic:**
- every 30–60 seconds: `SELECT ... FOR UPDATE SKIP LOCKED` due jobs
- execute → mark done
- on failure: `attempts++`, exponential backoff

## C) Access control
- Use `users.role` (admin/manager/user)
- Verify chat type:
  - In groups: only allow admin commands to group admins or your allowed list
  - In private: allow user commands

# #126 Permit/License Renewal Reminder Bot (B2B “never miss expiry”)

## Concept Overview
Track permits/licences/renewals (business, safety, insurance, certifications) and auto-remind responsible people before expiry.

## Problem It Solves
- Missed renewals cause fines/closures
- Expiry dates live in spreadsheets nobody checks

## MVP Features
**Phase 1 (Week 1–2)**
- Add “Permit”: name, authority, expiry date, responsible person, notes
- Reminder schedule: 30/14/7/1 days
- “Mark Renewed” flow (updates expiry + stores proof file)

**Phase 2 (Week 3–4)**
- Multiple permits per company + roles
- Monthly “upcoming renewals” report to admin chat

**Phase 3 (Week 5–8)**
- Mini App dashboard (optional) for filtering/export (validate `initData`) 

## Architecture
- Bot (CRUD permits) + Job runner (reminders) + Admin exports

## Database
- `companies(id, name, plan)`
- `users(id, telegram_id, company_id, role, timezone)`
- `permits(id, company_id, title, authority, expires_at, owner_user_id, status)`
- `permit_files(id, permit_id, tg_file_id, uploaded_at)`
- `jobs(...)` (for reminders)

## Development Steps
- Week 1: `/add_permit` wizard (FSM) + list view + edit
- Week 2: job scheduling on create/update; reminder messages with buttons:
  - ✅ Renewed (asks new expiry + optional file)
  - ⏰ Snooze 3 days
- Week 3: `/export_csv` (admin only)
- Week 4: billing gate (free: 5 permits; paid: unlimited)

## Monetization (simple)
- $19/mo per company up to 20 permits
- $49/mo unlimited + multi-admin

## Pitfalls
- Timezone errors: store `expires_at` in UTC, schedule reminders based on company timezone.
- Audit trail: keep `permit_events` if renewals are compliance-sensitive.

## Shared pipeline for #131–#137 (file/media bots)
File bots are profitable **if you build a solid pipeline**:

### File processing steps (robust MVP)
1) User uploads → store Telegram `file_id`, filename, size
2) Create `processing_job` row
3) Worker downloads file via `getFile` URL
4) Process with tool (FFmpeg, ImageMagick, LibreOffice, Tesseract)
5) Upload result back to Telegram (sendDocument/sendPhoto)
6) Cache results for re-download (“My Files”)

**DB tables**
- `uploads(id, user_id, tg_file_id, kind, status, meta_json, created_at)`
- `processing_jobs(id, upload_id, type, status, output_tg_file_id, error)`
